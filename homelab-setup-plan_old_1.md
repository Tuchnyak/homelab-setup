## Глава 0: Подготовка

На этом этапе мы подготовим все необходимое для установки операционной системы.

### 1. Загрузка образа Ubuntu Server

Всегда используйте LTS (Long-Term Support) версию для максимальной стабильности и долгосрочной поддержки.
- **Ссылка для загрузки:** [https://ubuntu.com/download/server](https://ubuntu.com/download/server)
- **Рекомендуемая версия:** Последняя доступная LTS.

### 1.1. Проверка целостности образа (Рекомендуется)

Чтобы убедиться, что скачанный файл не был поврежден при загрузке и не содержит вредоносных изменений, рекомендуется проверить его контрольную сумму.

1.  На странице загрузки Ubuntu найдите ссылку `SHA256SUMS` (обычно она находится рядом с кнопкой скачивания или в списке файлов).
2.  Откройте терминал (или PowerShell в Windows) в папке со скачанным образом.
3.  Выполните команду для расчета хеша вашего файла:
    * **Linux / macOS:**
        ```bash
        shasum -a 256 ubuntu-24.04.1-live-server-amd64.iso
        ```
    * **Windows:**
        ```powershell
        CertUtil -hashfile ubuntu-24.04.1-live-server-amd64.iso SHA256
        ```
    *(Замените имя файла на точное название скачанного вами образа).*
4.  Сравните полученную строку символов с той, что указана в файле `SHA256SUMS` на сайте. Они должны совпадать полностью.

### 2. Создание загрузочной USB-флешки

Вам понадобится USB-флешка объемом не менее 4 ГБ. Процесс создания загрузочного диска уничтожит все данные на ней.

- **Рекомендуемый инструмент:** [BalenaEtcher](https://www.balena.io/etcher/). Это кроссплатформенное приложение с простым графическим интерфейсом.
- **Процесс:**
    1.  Скачайте и установите BalenaEtcher.
    2.  Выберите скачанный `.iso` образ Ubuntu Server.
    3.  Выберите вашу USB-флешку.
    4.  Нажмите "Flash!" и дождитесь окончания процесса.

### 3. Требования к оборудованию (наш конфиг)
- **CPU:** AMD Ryzen 5 3500U (4 cores)
- **RAM:** 16 GB DDR4
- **Storage:** 1 TB PCIe3 NVMe SSD
- **Сеть:** Проводное подключение к вашему роутеру (настоятельно рекомендуется для стабильности).

## Глава 1: Установка и базовая настройка системы

Теперь мы установим операционную систему на наш сервер, выберем файловую систему Btrfs для снапшотов и выполним первые, самые важные настройки, включая Wi-Fi и статический IP.

### 1. Пошаговая установка Ubuntu Server с Btrfs

Подключите сервер к монитору и клавиатуре, вставьте загрузочную флешку и включите его. В BIOS/UEFI выберите загрузку с USB-носителя.

- [ ] **Язык:** Выберите `English`. Использование английского языка для системного интерфейса является стандартом в администрировании и избавляет от проблем с кодировками в консоли.
- [ ] **Раскладка клавиатуры:** Выберите свою раскладку или оставьте `English (US)`.
- [ ] **Тип установки:** Выберите `Ubuntu Server` (не `Ubuntu Server (minimized)`).
- [ ] **Сеть:** Установщик попытается настроить сеть. Поскольку проводное подключение недоступно, он, скорее всего, не сможет получить IP-адрес. **Это нормально.** Мы настроим Wi-Fi вручную после установки.
- [ ] **Прокси:** Оставьте поле пустым (`Leave blank`).
- [ ] **Зеркало Ubuntu:** Адрес по умолчанию подходит (`Default is fine`).
- [ ] **Диски и разделы (ВАЖНО: Настройка Btrfs):**
    - Выберите `Custom storage layout` (Ручная разметка).
    - Найдите ваш SSD (например, `/dev/nvme0n1` или `/dev/sda`).
    - Создайте новый раздел для загрузчика (Boot Partition):
        - Выберите диск, затем `Add GPT Partition`.
        - **Size:** `1GB`
        - **Format:** `ext4`
        - **Mount point:** `/boot`
    - Создайте новый раздел для Btrfs:
        - Выберите оставшееся свободное место на диске.
        - **Size:** Оставьте максимальный доступный размер.
        - **Format:** `btrfs`.
        - **Mount point:** `/` (root).
        - Убедитесь, что опция `Create subvolume for /home` (или аналогичная) **включена**. Это создаст отдельные subvolume для `/` и `/home`, что является хорошей практикой для Btrfs.
    - Проверьте и подтвердите схему разделов.
- [ ] **Настройка профиля:**
    - **Your name:** Ваше имя.
    - **Your server's name:** Придумайте имя для сервера, например, `homeserver`. Это имя будет видно в сети.
    - **Pick a username:** **Создайте вашего основного пользователя.** Не используйте `root` или `admin`. Например, `tuchnyak`.
    - **Choose a password:** **Создайте очень надежный пароль.** Это критически важно для безопасности.
- [ ] **Установка OpenSSH:**
    - **ОБЯЗАТЕЛЬНО** поставьте галочку на `Install OpenSSH server`. Это позволит нам подключаться к серверу удаленно.
    - **Не импортируйте** SSH-ключи на этом этапе, мы настроим их позже вручную.
- [ ] **Дополнительное ПО (Server Snaps):** Ничего не выбирайте. Мы не будем использовать Snap для наших сервисов.
- [ ] **Завершение:** Дождитесь окончания установки, после чего установщик попросит вас извлечь USB-носитель и нажать `Enter` для перезагрузки.

После перезагрузки вы увидите черный экран с приглашением для входа в систему. Установка завершена.

> **💡 Ethernet или Wi-Fi: что выбрать?**
>
> **Если есть возможность — подключите сервер Ethernet-кабелем.** Это всегда будет самый стабильный и быстрый вариант.
>
> **Но если вы живете на съемной квартире, роутер стоит в неудобном месте или принадлежит провайдеру — не переживайте.** Современный Wi-Fi (особенно Wi-Fi 5/6) при хорошем уровне сигнала отлично справляется с задачами домашнего сервера, включая стриминг 4K-видео. Этот гайд написан как раз для такой "реальной" ситуации.

### 2. Первый вход, настройка Wi-Fi и статического IP

Поскольку проводное подключение недоступно, мы настроим Wi-Fi и статический IP-адрес сразу после первого входа.

- [ ] **Первый вход в систему:** Войдите в систему на сервере, используя созданные вами имя пользователя и пароль.
- [ ] **Определите имя вашего Wi-Fi интерфейса:**
    ```bash
    ip a
    ```
    Найдите в выводе ваш Wi-Fi адаптер. Он может называться `wlan0`, `wlp1s0`, `wlo1` или похоже. Запишите это имя (например, `wlo1`).
- [ ] **Определите имя вашей Wi-Fi сети (SSID) и пароль.**
- [ ] **Проверьте, свободен ли выбранный IP-адрес.**
    Прежде чем присвоить серверу адрес `192.168.1.100`, критически важно убедиться, что он не занят другим устройством в вашей сети. Выполните эту проверку **на вашем основном компьютере** (с которого вы читаете эту инструкцию).
    * **Базовая проверка (Windows/macOS/Linux):**
        ```bash
        ping -c 3 192.168.1.100
        ```
        Если вы видите сообщения "Destination Host Unreachable" (Узел недоступен) или "Request timed out" (Превышен интервал ожидания) — скорее всего, адрес свободен. Если идут успешные ответы — адрес занят, выберите другой (например, `.101`).

    * **Продвинутая проверка (Linux/macOS — команда `arping`):**
        Это более надежный метод, так как некоторые устройства блокируют ping, но отвечают на ARP-запросы.
        ```bash
        # Требуются права администратора/root
        # Замените eth0 на имя вашего сетевого интерфейса на ПК
        sudo arping -c 3 -I eth0 192.168.1.100
        ```
        Если ответов нет (0 packets received) — адрес свободен.
- [ ] **Создайте резервную копию текущего файла Netplan:**
    ```bash
    sudo cp /etc/netplan/00-installer-config.yaml /etc/netplan/00-installer-config.yaml.bak
    ```
- [ ] **Отредактируйте файл конфигурации Netplan:**
    ```bash
    sudo vim /etc/netplan/00-installer-config.yaml
    ```
    Приведите его к следующему виду. **Внимание: Используйте только пробелы для отступов! Символы Tab сломают конфигурацию.**

    ```yaml
    # This is the network config written by 'subiquity'
    network:
        version: 2
        renderer: networkd
        wifis:
            # Замените wlo1 на имя вашего Wi-Fi интерфейса, которое вы определили выше
            wlo1:
                dhcp4: no
                access-points:
                    # Замените "YOUR_WIFI_SSID" на точное имя вашей Wi-Fi сети
                    "YOUR_WIFI_SSID":
                        # Замените "YOUR_WIFI_PASSWORD" на пароль от вашей Wi-Fi сети
                        password: "YOUR_WIFI_PASSWORD"
                addresses:
                    # Выбираем статический IP-адрес 192.18.1.100 с маской подсети /24
                    - 192.168.1.100/24
                routes:
                    - to: default
                      via: 192.168.1.1 # IP-адрес вашего роутера (шлюз)
                nameservers:
                    # DNS-серверы. Можно использовать DNS вашего роутера или публичные.
                    addresses: [192.168.1.1, 8.8.8.8]
    ```
    **Пояснения к выбору IP-адреса и маски:**
    *   **`192.168.1.100`**: Мы выбрали этот IP-адрес, так как он находится в твоей локальной сети (`192.168.1.x`) и достаточно далек от типичных адресов, выдаваемых роутером по DHCP, что снижает вероятность конфликтов.
    *   **`/24`**: Это маска подсети. Она означает, что все устройства с IP-адресами от `192.168.1.0` до `192.168.1.255` находятся в одной локальной сети и могут общаться напрямую.
    *   **`192.168.1.1`**: Это IP-адрес твоего роутера (шлюза по умолчанию), через который сервер будет выходить в интернет.

- [ ] **Примените конфигурацию Netplan:**
    ```bash
    # Сначала проверяем конфигурацию без разрыва соединения
    sudo netplan try
    # Если команда выше завершилась успешно (не разорвала SSH), применяем окончательно
    sudo netplan apply
    ```
    Если вы потеряли соединение с сервером (например, если вы уже пытались подключиться по SSH с другого компьютера), значит, где-то ошибка в конфиге. Проверьте его через прямое подключение к серверу.
- [ ] **Проверьте сетевое подключение:**
    ```bash
    ip a
    ping google.com -c 4
    ```
    Вы должны увидеть, что ваш Wi-Fi интерфейс (`wlo1` или как вы его назвали) имеет IP-адрес `192.168.1.100`, и пинг до Google проходит успешно.

### 3. Обновление системы и установка базовых утилит

Теперь, когда у сервера есть постоянный IP-адрес и доступ в интернет, можно продолжить настройку удаленно с вашего основного компьютера.

- [ ] **Подключитесь по SSH.** Откройте терминал на вашем компьютере и подключитесь к серверу:
    ```bash
    # Замените tuchnyak на ваше имя пользователя
    ssh tuchnyak@192.168.1.100
    ```
    При первом подключении потребуется подтвердить отпечаток ключа сервера, написав `yes`.
- [ ] **Обновите систему.** Это первое, что нужно сделать на свежей системе.
    ```bash
    sudo apt update
    sudo apt upgrade -y
    ```
- [ ] **Установите базовые утилиты.** Они пригодятся нам в дальнейшем.
    ```bash
    sudo apt install -y vim git curl wget htop net-tools tree
    ```

Теперь у вашего сервера есть постоянный адрес, доступ в интернет, и мы готовы к настройке безопасности.

### 4. Настройка автоматических Btrfs-снапшотов (Snapper)

Мы выбрали Btrfs ради возможности "откатить" систему в случае сбоя. Теперь мы настроим автоматическое создание таких точек восстановления с помощью `snapper`.

- [ ] **Установите Snapper и хук для `apt`:**
    ```bash
    sudo apt install -y snapper apt-btrfs-snapshot
    ```

- [ ] **Создайте конфигурацию Snapper для корневого раздела (`/`):**
    ```bash
    # Эта команда создаст файл конфигурации в /etc/snapper/configs/root
    sudo snapper -c root create-config /
    ```

- [ ] **Проверьте конфигурацию:**
    Откройте `/etc/snapper/configs/root` и убедитесь, что `snapper` правильно определил вашу файловую систему.
    ```bash
    sudo vim /etc/snapper/configs/root
    ```
    *Особенно обратите внимание на строку `SUBVOLUME="/"`.*

- [ ] **Настройте расписание автоматических снапшотов:**
    В том же файле `/etc/snapper/configs/root` найдите секцию `TIMELINE_CREATE`. Установите ее в `yes`, чтобы включить почасовые/ежедневные снапшоты.
    ```
    # (Было)
    TIMELINE_CREATE="no"
    # (Стало)
    TIMELINE_CREATE="yes"
    ```
    Также можно настроить лимиты хранения (сколько почасовых, ежедневных и т.д. снапшотов хранить), но значения по умолчанию уже достаточно хороши для старта.

- [ ] **Включите и запустите таймер `snapper`:**
    ```bash
    sudo systemctl enable --now snapper-timeline.timer
    sudo systemctl enable --now snapper-cleanup.timer
    ```
    *`snapper-timeline.timer` создает снапшоты по расписанию, `snapper-cleanup.timer` удаляет старые.*

- [ ] **Проверьте, что все работает:**
    ```bash
    # Показать список конфигураций
    sudo snapper list-configs
    # Вывод должен быть: root | /

    # Показать список снапшотов (пока будет 1-2)
    sudo snapper -c root list
    ```
    Теперь система будет автоматически создавать снапшоты до и после каждого выполнения `apt`, а также по расписанию.

### 5. Настройка Swap-файла для защиты от нехватки RAM

Наш сервер имеет 16 ГБ оперативной памяти. Этого достаточно для большинства задач, но при одновременном запуске нескольких "тяжелых" сервисов (вроде Nextcloud, Jellyfin и будущих LLM) память может закончиться. Чтобы система в такой ситуации не начала аварийно завершать процессы (OOM Killer), мы создадим "страховку" — swap-файл на диске.

#### Вариант 1: Классический Swap-файл (Рекомендуется)

Это создаст на вашем быстром NVMe SSD файл подкачки размером 8 ГБ.

- [ ] **Создайте и активируйте swap-файл:**
    ```bash
    # Выделяем файл размером 8 ГБ
    sudo fallocate -l 8G /swapfile
    # Устанавливаем правильные права доступа
    sudo chmod 600 /swapfile
    # Форматируем файл как swap
    sudo mkswap /swapfile
    # Включаем swap
    sudo swapon /swapfile
    ```
- [ ] **Проверьте, что swap активен:**
    ```bash
    sudo swapon --show
    free -h
    ```
    Вы должны увидеть ваш swap-файл в списке.
- [ ] **Сделайте swap постоянным (чтобы он включался после перезагрузки):**
    ```bash
    # Добавляем запись в /etc/fstab
    echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
    ```

#### Вариант 2: ZRAM (Продвинутый, для лучшей производительности)

ZRAM — это модуль ядра Linux, который создает сжатый блок в оперативной памяти. Он работает значительно быстрее, чем swap на диске, и используется для перемещения данных, к которым давно не обращались, но которые могут понадобиться снова. Это может немного повысить общую отзывчивость системы под нагрузкой.

- [ ] **Установите утилиты для управления ZRAM:**
    ```bash
    sudo apt install zram-tools
    ```
- [ ] **Настройте ZRAM.** Откройте файл конфигурации:
    ```bash
    sudo vim /etc/default/zramswap
    ```
    Измените параметр `ALGO` на `zstd` (более современный алгоритм сжатия) и `PERCENT` на `25` (выделить 25% от ОЗУ под zram, т.е. 4 ГБ).
    ```
    ALGO=zstd
    PERCENT=25
    ```
- [ ] **Перезапустите сервис, чтобы применить изменения:**
    ```bash
    sudo systemctl restart zramswap.service
    ```
> **Рекомендация:** Лучше всего использовать **оба метода**. ZRAM будет служить быстрым кэшем для неактивных страниц памяти, а swap-файл на диске — надежной страховкой от критической нехватки памяти. Они отлично дополняют друг друга.

## Глава 2: Безопасность и удаленный доступ

На этом этапе мы "закалим" наш сервер, сделав его устойчивым к атакам извне и настроив безопасный и удобный способ подключения.

### 1. Настройка SSH-доступа по ключам

Вход по паролю уязвим для брутфорс-атак (автоматического подбора). SSH-ключи — на порядок более безопасный метод аутентификации.

- [ ] **Создайте пару ключей на вашем компьютере (не на сервере).** Если у вас их еще нет, выполните в терминале вашего ПК:
    ```bash
    # Нажмите Enter на все вопросы, чтобы принять значения по умолчанию.
    ssh-keygen -t rsa -b 4096
    ```
    Эта команда создаст приватный (`id_rsa`) и публичный (`id_rsa.pub`) ключи в папке `~/.ssh/`.

- [ ] **Скопируйте публичный ключ на сервер.** Это можно сделать одной командой с вашего ПК:
    ```bash
    # Замените username и server_ip на ваши
    ssh-copy-id tuchnyak@192.168.1.100
    ```
    Вас попросят ввести пароль от пользователя на сервере в последний раз.

- [ ] **Проверьте, что вход по ключу работает.** Попробуйте снова подключиться к серверу. На этот раз он не должен спрашивать пароль:
    ```bash
    ssh tuchnyak@192.168.1.100
    ```

- [ ] **Отключите вход по паролю на сервере.** Это критически важный шаг.
    ```bash
    # Открываем конфигурационный файл SSH
    sudo vim /etc/ssh/sshd_config
    ```
    Найдите в файле следующие строки и приведите их к такому виду (раскомментируйте, убрав `#`, и измените значение на `no`):
    ```
    PasswordAuthentication no
    PermitEmptyPasswords no
    ChallengeResponseAuthentication no
    ```
    Сохраните файл и **перезапустите SSH-сервис**:
    ```bash
    sudo systemctl restart sshd
    ```
    **ПРОВЕРКА:** Откройте **новое окно терминала** (не закрывая текущее!) и попробуйте подключиться. Если все прошло успешно, вы подключитесь без пароля. Если есть ошибка, вы сможете исправить ее в старом окне.

### 2. Настройка файрвола UFW

UFW (Uncomplicated Firewall) — это простой и мощный инструмент для управления доступом к портам сервера.

- [ ] **Установите политику по умолчанию.** Запретим все входящие соединения и разрешим все исходящие.
    ```bash
    sudo ufw default deny incoming
    sudo ufw default allow outgoing
    ```

- [ ] **Создайте резервную копию файла конфигурации UFW перед изменениями:**
    ```bash
    sudo cp /etc/ufw/before.rules /etc/ufw/before.rules.bak
    sudo cp /etc/ufw/after.rules /etc/ufw/after.rules.bak
    sudo cp /etc/default/ufw /etc/default/ufw.bak
    ```

- [ ] **Добавьте необходимые правила.** Нам нужно разрешить подключения к SSH, а также к веб-серверу (HTTP/HTTPS), который мы настроим позже.
    ```bash
    # Разрешаем SSH (порт 22)
    sudo ufw allow ssh 
    
    # Разрешаем HTTP (порт 80)
    sudo ufw allow http

    # Разрешаем HTTPS (порт 443)
    sudo ufw allow https
    ```

- [ ] **Включите файрвол.**
    ```bash
    sudo ufw enable
    ```
    Система предупредит, что это может разорвать текущее SSH-соединение. Согласитесь (`y`), так как мы уже создали разрешающее правило.

- [ ] **Проверьте статус.**
    ```bash
    sudo ufw status verbose
    ```
    Вы должны увидеть, что файрвол активен и ваши правила применены.

### 3. Установка и настройка Fail2ban

Fail2ban — это сервис, который анализирует логи и автоматически блокирует IP-адреса, с которых идут повторяющиеся попытки входа (брутфорс).

- [ ] **Установка.**
    ```bash
    sudo apt install -y fail2ban
    ```

- [ ] **Создание локального конфига.** Никогда не редактируйте стандартный `jail.conf`. Вместо этого создайте его локальную копию.
    ```bash
    sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local
    ```

- [ ] **Настройка.** Откройте новый файл для редактирования:
    ```bash
    sudo vim /etc/fail2ban/jail.local
    ```
    В этом файле можно тонко настроить параметры блокировки. Для начала достаточно убедиться, что секция `[sshd]` включена (`enabled = true`). По умолчанию она уже активна и будет защищать наш SSH-сервис.

- [ ] **Запустите и проверьте сервис.**
    ```bash
    sudo systemctl enable fail2ban
    sudo systemctl start fail2ban
    sudo systemctl status fail2ban
    ```
    Вы должны увидеть, что сервис активен. Теперь ваш сервер защищен от автоматического подбора паролей.

### 3.1. (Продвинуто) Защита веб-сервисов через Nginx Proxy Manager

> ⚠️ Важное примечание
> Укажи, что этот шаг (настройка jail для NPM) технически сработает только **после Главы 4**, когда Nginx Proxy Manager будет запущен и создаст файлы логов. Если сделать это сейчас, Fail2ban может не запуститься с ошибкой «No such file». Рекомендуй читателю вернуться к этому пункту позже или создать пустые файлы логов вручную командой `touch`.

Поскольку все наши веб-приложения будут работать через единую точку входа — Nginx Proxy Manager (NPM), мы можем настроить Fail2ban на анализ его логов. Это позволит банить IP-адреса, которые пытаются подобрать пароли к вашим сайтам или сканируют уязвимости.

**Важно:** Этот шаг подразумевает, что логи NPM будут находиться по пути `/srv/npm/data/logs`, который мы настроим в Главе 4. Если вы еще не настроили NPM, вернитесь к этому шагу позже или настройте его "на будущее".

- [ ] **Создайте фильтр для Nginx.**
    Сначала объясним Fail2ban, что считать "атакой" в логах веб-сервера (частые ошибки 401, 403, 404).
    ```bash
    sudo vim /etc/fail2ban/filter.d/npm-general.conf
    ```
    Вставьте содержимое:
    ```ini
    [Definition]
    # Баним за попытки входа (401), запрещенный доступ (403) и сканирование несуществующих страниц (404)
    failregex = ^<HOST> .* "(GET|POST|HEAD).*HTTP.*" (401|403|404) .*$
    ignoreregex =
    ```

- [ ] **Активируйте защиту в `jail.local`.**
    Откройте ваш файл конфигурации:
    ```bash
    sudo vim /etc/fail2ban/jail.local
    ```
    Добавьте в конец файла новую секцию:
    ```ini
    [npm-general]
    enabled = true
    filter = npm-general
    # Блокируем нарушителя на всех портах (http, https)
    action = iptables-allports[name=npm-general]
    # Путь к логам NPM (настраивается в Главе 4)
    logpath = /srv/npm/data/logs/proxy-host-*_access.log
              /srv/npm/data/logs/fallback_access.log
    maxretry = 10
    findtime = 600
    bantime = 3600
    ```

- [ ] **Перезапустите Fail2ban.**
    ```bash
    sudo systemctl restart fail2ban
    ```
    Теперь ваш сервер будет автоматически блокировать "ботов-сканеров" и любителей подбирать пароли к веб-интерфейсам.

### 4. (Опционально) Изменение порта SSH

Изменение стандартного порта SSH (22) может снизить количество автоматических атак и "шума" в логах. Это не является критически важной мерой безопасности, но может быть полезным.

- [ ] **Выберите новый порт.** Выберите любой порт в диапазоне от 1024 до 65535, который не используется другими сервисами. Например, `2222`.
- [ ] **Создайте резервную копию файла конфигурации SSH:**
    ```bash
    sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak_before_port_change
    ```
- [ ] **Отредактируйте конфигурационный файл SSH:**
    ```bash
    sudo vim /etc/ssh/sshd_config
    ```
    Найдите строку `#Port 22` (или `Port 22`), раскомментируйте ее (если нужно) и измените на ваш новый порт:
    ```
    Port 2222 # Замените 2222 на выбранный вами порт
    ```
    **ВАЖНО:** Не удаляйте старую строку `Port 22` сразу. Сначала убедитесь, что новый порт работает.
- [ ] **Добавьте новое правило в UFW для нового порта SSH:**
    ```bash
    sudo ufw allow 2222/tcp # Замените 2222 на ваш новый порт
    sudo ufw reload
    ```
- [ ] **Перезапустите SSH-сервис:**
    ```bash
    sudo systemctl restart sshd
    ```
- [ ] **ПРОВЕРКА:** Откройте **новое окно терминала** и попробуйте подключиться к серверу, указав новый порт:
    ```bash
    ssh -p 2222 tuchnyak@192.168.1.100 # Замените 2222 на ваш новый порт
    ```
    Если подключение успешно, вы можете вернуться к редактированию `/etc/ssh/sshd_config` и **закомментировать или удалить старую строку `Port 22`**, а затем снова перезапустить SSH-сервис.
- [ ] **Удалите старое правило UFW (опционально):**
    ```bash
    sudo ufw delete allow ssh # Удалит правило для порта 22
    sudo ufw reload
    ```

## Глава 3: Фундамент для сервисов

Сервер защищен, теперь пора готовить плацдарм для наших будущих приложений. Мы создадим специальное место для хранения их данных, установим систему контейнеризации, веб-интерфейс для удобного управления и терминальный мультиплексор для комфортной работы.

### 1. Создание структуры каталогов в `/srv`

Чтобы данные наших сервисов не были разбросаны по всей системе, мы будем хранить их централизованно в директории `/srv` (от англ. "serve"). Это стандартная практика для данных, которые сервер предоставляет пользователям или другим сервисам.

- [ ] **Создайте родительскую директорию `/srv`**, если она еще не существует.
    ```bash
    sudo mkdir -p /srv
    ```

- [ ] **Создайте поддиректории для каждого сервиса.**
    ```bash
    sudo mkdir -p /srv/nextcloud
    sudo mkdir -p /srv/jellyfin/config
    sudo mkdir -p /srv/jellyfin/media
    sudo mkdir -p /srv/qbittorrent/config
    sudo mkdir -p /srv/qbittorrent/downloads
    sudo mkdir -p /srv/syncthing/config
    sudo mkdir -p /srv/syncthing/data
    sudo mkdir -p /srv/npm/data
    sudo mkdir -p /srv/npm/letsencrypt
    ```
    *Примечание: некоторым сервисам, как Jellyfin, нужны отдельные папки для конфигурации и для медиафайлов. Мы будем использовать `/srv/jellyfin/media` как общую папку для фильмов и сериалов.*

- [ ] **Назначьте владельцем этих директорий вашего пользователя.** Это важно, чтобы избежать проблем с правами доступа, когда мы будем запускать контейнеры от вашего имени (rootless).
    ```bash
    # Рекурсивно (-R) меняем владельца для /srv и всего, что внутри
    sudo chown -R $USER:$USER /srv
    ```

### 2. Установка Podman и Podman-Compose

Podman — это современный и безопасный движок для запуска контейнеров, который является прямой заменой Docker.

- [ ] **Установите Podman.**
    ```bash
    sudo apt install -y podman
    ```

- [ ] **Установите Podman-Compose.** Это аналог `docker-compose`, который позволяет управлять наборами контейнеров с помощью YAML-файлов.
    ```bash
    # Устанавливаем pip, менеджер пакетов Python, для установки podman-compose
    sudo apt install -y python3-pip
    # Устанавливаем сам podman-compose
    pip install podman-compose
    ```

- [ ] **Проверьте установку.**
    ```bash
    podman --version
    podman-compose --version
    ```
    Команды должны вернуть версии установленных пакетов.

### 3. Установка и настройка Cockpit

Cockpit — это легковесная и мощная веб-панель для управления сервером. Через нее удобно следить за состоянием системы и управлять контейнерами.

- [ ] **Установите Cockpit и плагин для Podman.**
    ```bash
    sudo apt install -y cockpit cockpit-podman
    ```

- [ ] **Откройте порт для Cockpit в файрволе.** Cockpit по умолчанию работает на порту 9090. Мы разрешим доступ к нему только из локальной сети.
    ```bash
    # Диапазон 192.168.0.0/16 покрывает все адреса от 192.168.0.1 до 192.168.255.254
    sudo ufw allow from 192.168.0.0/16 to any port 9090
    sudo ufw reload
    ```

- [ ] **Проверьте доступ.** Откройте в браузере на вашем ПК адрес: `https://ВАШ_СЕРВЕР_IP:9090`.
    - Вы увидите предупреждение о самоподписанном сертификате. Это нормально, смело принимайте его.
    - Войдите в систему, используя **имя пользователя и пароль вашего пользователя на сервере**.
    - После входа вы увидите панель с состоянием сервера. Перейдите в раздел "Podman containers", чтобы убедиться, что плагин работает.

- [ ] **Оцените доступные ресурсы (ОЗУ).**
    Перейдите на вкладку "Overview" (Обзор). Найдите график "Memory" (Память).
    > **⚠️ Критически важно:** У вашего сервера 16 ГБ оперативной памяти. Это ваше главное ограничение ("бутылочное горлышко").
    > Возьмите за правило заглядывать на эту вкладку **каждый раз после запуска нового сервиса**. Если свободная память упадет ниже 2 ГБ, система может начать тормозить или принудительно закрывать приложения (OOM Killer).

### 4. Установка терминального мультиплексора Zellij (Рекомендуется)

Zellij — это современный терминальный мультиплексор, который позволяет сохранять вашу рабочую сессию на сервере. Это защищает от разрыва соединения и позволяет отключаться от сервера, оставляя запущенные процессы работать.

- [ ] **Установите Zellij.** Мы скачаем последнюю версию с GitHub.
    ```bash
    # Переходим в домашнюю директорию
    cd ~
    # Скачиваем архив с последней версией
    wget https://github.com/zellij-org/zellij/releases/latest/download/zellij-x86_64-unknown-linux-musl.tar.gz
    # Распаковываем архив
    tar -xvf zellij-x86_64-unknown-linux-musl.tar.gz
    # Перемещаем исполняемый файл в директорию, которая есть в PATH
    sudo mv zellij /usr/local/bin/
    # Удаляем скачанный архив
    rm zellij-x86_64-unknown-linux-musl.tar.gz
    ```

- [ ] **Базовое использование:**
    - **Запустить новую сессию:** Просто введите `zellij`.
    - **Отключиться от сессии (оставив ее работать):** Нажмите `Ctrl+o`, затем `d` (detach).
    - **Подключиться к существующей сессии:** Введите `zellij attach`.

Чтобы работа с текстовыми файлами на сервере не вызывала дискомфорта, настроим Vim.

На этом этапе наш фундамент готов. У нас есть безопасная система, удобный веб-интерфейс и мощные инструменты для запуска изолированных приложений и управления сервером.

## Глава 4: Сетевая инфраструктура и файловый доступ

Теперь, когда "фундамент" готов, пора строить "стены": настроить единую точку входа для всех сервисов, защитить ее с помощью SSL и обеспечить удобный способ загрузки файлов на сервер.

### 1. Развертывание Nginx Proxy Manager (NPM)

NPM — это мощный, но простой в управлении обратный прокси с веб-интерфейсом. Он будет принимать все запросы из вашей сети и распределять их по нужным контейнерам.

- [ ] **Создайте директорию для `podman-compose` файлов.** Хорошей практикой является хранить все конфигурационные файлы в одном месте.
    ```bash
    mkdir -p ~/compose/npm
    cd ~/compose/npm
    ```

- [ ] **Создайте файл `.env` для NPM.** (Для NPM обычно не требуются пароли в `podman-compose.yml`, но мы создадим файл для единообразия и будущих настроек).
    ```bash
    vim .env
    ```
    Добавьте, например, пустую строку или комментарий:
    ```
    # Nginx Proxy Manager environment variables
    ```
    Сохраните и закройте файл.

- [ ] **Защитите файл `.env` правами доступа.**
    ```bash
    chmod 600 .env
    ```

- [ ] **Создайте `podman-compose.yml` для NPM.**
    ```bash
    vim podman-compose.yml
    ```
    Вставьте в него следующее содержимое:
    ```yaml
    version: "3"
    services:
      npm:
        image: 'jc21/nginx-proxy-manager:latest'
        container_name: npm
        restart: unless-stopped
        ports:
          # Порт для админки
          - '81:81'
          # Стандартные порты HTTP и HTTPS
          - '80:80'
          - '443:443'
        volumes:
          - /srv/npm/data:/data
          - /srv/npm/letsencrypt:/etc/letsencrypt
    ```

- [ ] **Запустите контейнер.**
    ```bash
    podman-compose up -d
    ```
    Ключ `-d` (detach) запускает контейнер в фоновом режиме.

- [ ] **Первичная настройка NPM.**
    - Откройте в браузере `http://192.168.1.100:81`.
    - Войдите, используя стандартные учетные данные:
        - **Email:** `admin@example.com`
        - **Password:** `changeme`
    - Сразу после входа система попросит вас сменить email и пароль. **Сделайте это обязательно.**

### 2. HTTPS для локальных доменов (*.internal)

Чтобы доступ к нашим сервисам был безопасным (например, по адресу `https://jellyfin.internal`), нам нужен SSL-сертификат. Однако стандартный способ его получения (через Let's Encrypt) требует, чтобы ваш сервер был виден из глобального интернета, что в нашем случае не так.

Эта проблема — одна из главных сложностей при настройке домашнего сервера. Ниже описаны три способа ее решения, от самого простого и надежного до компромиссных.

#### Вариант 1 (Рекомендуемый): Локальный центр сертификации с `mkcert`

Этот метод заключается в том, что мы превращаем наш собственный компьютер в доверенный центр сертификации (CA), который может выпускать "настоящие" сертификаты для наших локальных доменов. Браузер будет им полностью доверять.

**Принцип работы:**
1.  На **вашем основном компьютере** (не на сервере!) мы устанавливаем утилиту `mkcert`.
2.  `mkcert` создает локальный корневой сертификат (Local CA) и автоматически добавляет его в хранилища доверенных сертификатов вашей операционной системы и браузеров.
3.  Этим "ручным" центром сертификации мы подписываем сертификат для всех наших будущих доменов (`*.internal`).
4.  Готовый сертификат и его ключ мы просто загружаем в Nginx Proxy Manager.

**Шаг 1: Установка `mkcert` на ваш основной компьютер**

Откройте терминал на вашем ПК (Windows/macOS/Linux) и следуйте инструкции для вашей ОС.

*   **macOS (через Homebrew):**
    ```bash
    brew install mkcert
    ```
*   **Windows (через Chocolatey):**
    ```powershell
    choco install mkcert
    ```
*   **Linux (требуется `certutil`):**
    ```bash
    # Сначала установите certutil
    sudo apt install libnss3-tools -y
    # Затем установите mkcert
    # (Инструкции могут отличаться для разных дистрибутивов, см. документацию mkcert)
    ```

**Шаг 2: Создание локального CA**

Это самая важная команда. Она выполняется **один раз**. `mkcert` создаст ваш персональный центр сертификации и установит его в систему.
```bash
mkcert -install
```
Вы можете увидеть запрос на ввод пароля администратора — это необходимо для добавления CA в системное хранилище.

**Шаг 3: Генерация Wildcard-сертификата**

Теперь создадим сертификат, который будет действовать для **любого** поддомена в нашей локальной зоне `.internal`.

```bash
# Эта команда создаст два файла: _wildcard.internal.pem и _wildcard.internal-key.pem
mkcert "*.internal"
```

**Шаг 4: Загрузка сертификата в Nginx Proxy Manager**

1.  У вас в текущей папке на компьютере появились два файла:
    *   `_wildcard.internal.pem` (публичный сертификат)
    *   `_wildcard.internal-key.pem` (приватный ключ)
2.  Откройте веб-интерфейс NPM (`http://192.168.1.100:81`).
3.  Перейдите в `SSL Certificates` -> `Add SSL Certificate` -> `Custom`.
4.  **Придумайте имя (Nickname):** `Internal Wildcard Cert`
5.  **Certificate Key:** Откройте файл `_wildcard.internal-key.pem` текстовым редактором, скопируйте **все его содержимое** (включая `-----BEGIN PRIVATE KEY-----` и `-----END PRIVATE KEY-----`) и вставьте в это поле.
6.  **Certificate:** Откройте файл `_wildcard.internal.pem`, скопируйте **все его содержимое** и вставьте в это поле.
7.  Нажмите `Save`.

Готово! Теперь при настройке любого прокси-хоста (например, `jellyfin.internal`) на вкладке SSL вы сможете просто выбрать `Internal Wildcard Cert` из выпадающего списка. Ваш браузер будет показывать "зеленый замок" без каких-либо предупреждений.

> **📲 Доверие на других устройствах (телефоны, планшеты):**
> Чтобы ваш телефон или планшет также доверяли этому сертификату, вам нужно один раз импортировать на них корневой сертификат вашего CA. Чтобы найти его, выполните на ПК команду `mkcert -CAROOT` — она покажет путь к папке с файлом `rootCA.pem`. Этот файл нужно передать на мобильное устройство и установить как доверенный корневой сертификат в настройках безопасности.

#### Вариант 2 (Продвинутый): Публичный домен и DNS Challenge

Если у вас есть зарегистрированное доменное имя, вы можете использовать его поддомены для доступа к локальным сервисам и получать для них публичные сертификаты Let's Encrypt. Это работает через так называемый **DNS Challenge**.

- [ ] **Выберите DNS-провайдера.** Вам понадобится DNS-провайдер, который поддерживается NPM и предоставляет API-ключи. Примеры: Cloudflare, DigitalOcean, GoDaddy и многие другие.
- [ ] **Получите API-ключ от вашего DNS-провайдера.** Найдите в документации вашего провайдера, как создать API-токен или ключ.
- [ ] **Добавьте учетные данные в NPM.**
    - В веб-интерфейсе NPM перейдите в `SSL Certificates` -> `Add SSL Certificate` -> `Let's Encrypt`.
    - В поле `DNS Provider` выберите вашего провайдера.
    - Вставьте ваш API-ключ в соответствующее поле.
    - Согласитесь с условиями использования Let's Encrypt.
    - Нажмите `Save`.

Теперь NPM готов к выпуску SSL-сертификатов.

#### Вариант 3 (Не рекомендуется): Self-Signed сертификаты через NPM

NPM может сам генерировать самоподписанные (self-signed) сертификаты. Это самый быстрый, но и самый неудобный способ. Ваш браузер не будет доверять такому сертификату и будет показывать назойливое окно с предупреждением об угрозе безопасности **при каждом заходе** на каждый сервис. Этот вариант стоит использовать только для временных тестов.

### 3. Локальный DNS: чтобы `jellyfin.internal` работало везде

Мы настроили красивые имена для наших сервисов в Nginx Proxy Manager (например, `jellyfin.internal`), но есть проблема: ваш компьютер или телефон не знают, что это за адрес. Чтобы они заработали, нам нужен **локальный DNS-сервер**, который будет отвечать на запросы "*.internal" и указывать на IP-адрес нашего сервера.

Мы используем для этой цели **AdGuard Home**. Помимо решения нашей основной задачи, он также будет блокировать рекламу и трекеры во всей вашей домашней сети.

- [ ] **Освобождение 53 порта (Важно!)**
    Прежде чем мы запустим AdGuard, нужно освободить порт `53`, который по умолчанию занят системной службой `systemd-resolved`. Мы не сломаем сеть, а просто переключим сервер на использование внешних DNS напрямую.

    ```bash
    # 1. Отключаем локальный DNS-слушатель (освобождаем порт 53)
    sudo mkdir -p /etc/systemd/resolved.conf.d
    echo -e "[Resolve]\nDNSStubListener=no" | sudo tee /etc/systemd/resolved.conf.d/adguardhome.conf

    # 2. ВАЖНО: Подменяем resolv.conf, чтобы сервер использовал внешние DNS напрямую
    # Без этого шага интернет на сервере пропадет!
    sudo mv /etc/resolv.conf /etc/resolv.conf.backup
    sudo ln -s /run/systemd/resolve/resolv.conf /etc/resolv.conf

    # 3. Применяем изменения
    sudo systemctl reload-or-restart systemd-resolved
    ```

- [ ] **Создайте директории для AdGuard Home.**
    ```bash
    # Для данных
    sudo mkdir -p /srv/adguardhome/work
    sudo mkdir -p /srv/adguardhome/conf
    # Для compose-файла
    mkdir -p ~/compose/adguardhome
    cd ~/compose/adguardhome
    ```
- [ ] **Создайте `podman-compose.yml` для AdGuard Home.**
    ```bash
    vim podman-compose.yml
    ```
    Содержимое `podman-compose.yml`:
    ```yaml
    version: "3"
    services:
      adguardhome:
        image: adguard/adguardhome:latest
        container_name: adguardhome
        restart: unless-stopped
        mem_limit: 512m
        ports:
          - "53:53/tcp"
          - "53:53/udp"    # DNS-сервер
          - "3000:3000/tcp"  # Веб-интерфейс для настройки
        volumes:
          - /srv/adguardhome/work:/opt/adguardhome/work
          - /srv/adguardhome/conf:/opt/adguardhome/conf
    ```
- [ ] **Запустите контейнер.**
    ```bash
    podman-compose up -d
    ```
> 📈 **Контроль ресурсов:** Зайдите в Cockpit (`https://192.168.1.100:9090`), перейдите в раздел "Podman containers" и посмотрите, сколько памяти потребляет новый контейнер `adguardhome`. Убедитесь, что у системы осталось достаточно свободной ОЗУ.

- [ ] **Первичная настройка AdGuard Home.**
    1.  Откройте в браузере `http://192.168.1.100:3000`.
    2.  Пройдите мастер первоначальной настройки. На шаге "DNS Listen Interfaces" выберите ваш сетевой интерфейс (например, `wlo1` или `eth0`).
    3.  Придумайте логин и пароль для доступа к панели управления.

- [ ] **Настройка DNS-перезапросов (DNS Rewrites).**
    Это **ключевой шаг**.
    1.  В панели AdGuard Home перейдите в `Filters` -> `DNS rewrites`.
    2.  Нажмите `Add DNS Rewrite`.
    3.  В поле `Domain` введите `*.internal`.
    4.  В поле `IP address` введите `192.168.1.100`.
    5.  Нажмите `Save`.

Теперь AdGuard Home готов. Осталось "рассказать" вашим устройствам, что им нужно пользоваться.

- [ ] **Три способа заставить устройства использовать ваш новый DNS-сервер:**
    1.  **(Рекомендуемый) Вручную на каждом устройстве:** Это самый надежный способ. Вам нужно зайти в сетевые настройки вашего ПК, смартфона, телевизора и в качестве DNS-сервера указать `192.168.1.100`.
    2.  **(Если возможно) В настройках роутера:** Зайдите в веб-интерфейс вашего роутера. Найдите настройки DHCP-сервера. Если есть поле для указания DNS-сервера, который выдается клиентам, впишите туда `192.168.1.100`. После этого все устройства, получившие адрес по DHCP, будут автоматически использовать ваш AdGuard Home.
    3.  **(Запасной вариант) Файл `hosts`:** На каждом компьютере есть специальный файл `hosts`, где можно вручную прописать соответствие домена и IP. Это неудобно, так как для каждого нового сервиса (`jellyfin.internal`, `cloud.internal` и т.д.) придется добавлять новую строчку на каждом компьютере.

После того как вы настроите DNS одним из этих способов, адреса `https://jellyfin.internal`, `https://cloud.internal` и другие должны открываться на ваших устройствах без проблем.

### 4. Настройка Samba для файлового доступа

Samba — это реализация протокола SMB, который позволяет создавать "сетевые папки", доступные для Windows, macOS и Linux.

- [ ] **Установите Samba.**
    ```bash
    sudo apt install -y samba
    ```

- [ ] **Создайте резервную копию файла конфигурации Samba:**
    ```bash
    sudo cp /etc/samba/smb.conf /etc/samba/smb.conf.bak
    ```

    # Настройте Samba. Откройте главный конфигурационный файл:
    ```bash
    sudo vim /etc/samba/smb.conf
    ```
    
    В начало файла добавьте глобальные настройки безопасности:
    ```ini
    [global]
    # Запретить гостевой доступ полностью
    map to guest = never
    # Требовать шифрование для всех соединений
    server smb encrypt = required
    ```

    Пролистайте в самый конец файла и добавьте следующие блоки для создания сетевых папок:
    ```ini
    # Общая папка для медиафайлов (фильмы, сериалы, музыка)
    # Доступ на чтение и запись для всех доверенных пользователей.
    [Media]
    comment = Media files for Jellyfin
    path = /srv/jellyfin/media
    browseable = yes
    guest ok = no
    read only = no
    writable = yes
    create mask = 0755
    directory mask = 0755
    # Замените tuchnyak на список ваших пользователей через запятую,
    # например: valid users = tuchnyak, user2, @family_group
    valid users = tuchnyak

    # Папка для загрузок. Только для администратора.
    [Torrents]
    comment = Torrent downloads
    # Путь к папке загрузок qBittorrent
    path = /srv/qbittorrent/downloads
    browseable = yes
    guest ok = no
    read only = no
    writable = yes
    create mask = 0755
    directory mask = 0755
    # Указываем только вашего основного пользователя
    valid users = tuchnyak

    # Папка для бэкапов (например, с ваших ПК)
    # Может понадобиться в будущем.
    [Backups]
    comment = Client machine backups
    path = /srv/backups
    browseable = yes
    guest ok = no
    read only = no
    writable = yes
    create mask = 0755
    directory mask = 0755
    valid users = tuchnyak
    ```
    *Пояснение: Вместо одной большой папки `/srv` мы создали три целевые. Это безопаснее и удобнее. Убедитесь, что директория `/srv/backups` существует: `sudo mkdir -p /srv/backups && sudo chown $USER:$USER /srv/backups`.*

- [ ] **Создайте пароль для Samba.** Важно: этот пароль не связан с вашим системным паролем.
    ```bash
    # Замените tuchnyak на вашего пользователя
    sudo smbpasswd -a tuchnyak
    ```
    Вам будет предложено ввести и подтвердить новый пароль.

- [ ] **Перезапустите сервисы Samba.**
    ```bash
    sudo systemctl restart smbd
    sudo systemctl restart nmbd
    ```

- [ ] **Проверка доступа.**
    - **Windows:** Откройте "Проводник", в адресной строке введите `\\192.168.1.100\Media` и нажмите Enter. Введите ваше имя пользователя и Samba-пароль.
    - **macOS:** Откройте "Finder", нажмите `Cmd+K` и введите `smb://192.168.1.100/Media`.

Теперь вы можете легко перетаскивать файлы (фильмы, музыку, торренты) прямо на сервер, как в обычную папку.

## Глава 5: Развертывание основных сервисов

**Примечание о выборе домена:**
Мы будем использовать домен `.internal` для всех наших сервисов (например, `jellyfin.internal`, `cloud.internal`). Этот домен официально зарезервирован для частного использования и гарантированно никогда не будет конфликтовать с публичными интернет-доменами.

Пришло время заселять наш сервер жильцами. Мы будем использовать `podman-compose` для запуска каждого сервиса. Все `podman-compose.yml` файлы мы будем создавать в директории `~/compose`, которую создали в предыдущей главе.

**Общий принцип для всех сервисов:**
1.  Создаем для сервиса отдельную директорию внутри `~/compose`.
2.  Внутри нее создаем файл `.env` для хранения секретов.
    > **Примечание:** Для некоторых сервисов изначально не требуются секреты в `.env` файле. Тем не менее, мы создаем его для поддержания единообразия в структуре проекта и для удобства добавления переменных окружения в будущем, если это потребуется.
3.  Внутри нее создаем файл `podman-compose.yml`, ссылаясь на переменные из `.env`.
4.  Запускаем командой `podman-compose up -d`.
5.  Настраиваем доступ через Nginx Proxy Manager с использованием HTTPS.
6.  **Контроль ресурсов (Resource Check):**
    Сразу после запуска (`up -d`) открываем Cockpit и проверяем, насколько выросло потребление оперативной памяти. Если сервис "съел" неожиданно много, стоит изучить его настройки на предмет ограничения памяти (memory limits).

### 5. Автозапуск контейнеров при перезагрузке системы

Мы настроили все наши сервисы, но есть одна проблема: если сервер перезагрузится, ни один из контейнеров не запустится автоматически. Мы решим эту проблему с помощью `quadlets` — современного механизма интеграции Podman с `systemd`, который позволяет управлять контейнерами как обычными системными сервисами.

**Принцип работы:**
Вместо сложных `systemd-unit` файлов мы создаем простые текстовые файлы с расширением `.container` в специальной директории. `Podman` автоматически "превратит" их в полноценные сервисы `systemd`. Этот подход гораздо проще и нагляднее, чем `podman generate systemd`.

**Шаг 0: Остановка текущих контейнеров**
Прежде чем создавать системные сервисы, необходимо остановить все контейнеры, запущенные ранее через `podman-compose`. Podman не сможет запустить системный сервис, если контейнер с таким же именем (например, `npm` или `jellyfin`) уже работает.

Выполните следующие команды для всех ваших запущенных сервисов:
```bash
cd ~/compose/npm && podman-compose down
cd ~/compose/jellyfin && podman-compose down
cd ~/compose/qbittorrent && podman-compose down
cd ~/compose/nextcloud && podman-compose down
cd ~/compose/syncthing && podman-compose down
cd ~/compose/adguardhome && podman-compose down
# Повторить для всех запущенных сервисов
```

**Шаг 1: Создание `.container` файлов**

Поскольку мы запускаем контейнеры от нашего обычного пользователя (rootless), эти файлы должны находиться в `~/.config/containers/systemd/`.

## Глава 6: Стратегия резервного копирования

Работающий сервер — это хорошо, но сервер с надежными бэкапами — еще лучше. Наша архитектура с выносом всех данных в `/srv` делает процесс резервного копирования очень простым.

**Цель:** Автоматически создавать полную копию всех важных данных на внешний USB-диск.

### 1. Подготовка внешнего диска

Вам понадобится внешний USB-диск, объем которого достаточен для хранения копии ваших данных.

- [ ] **Подключите диск к серверу.**

- [ ] **Найдите имя диска в системе.**
    ```bash
    sudo fdisk -l
    ```
    Найдите ваш диск по размеру. Он будет иметь имя вроде `/dev/sda` или `/dev/sdb`.

- [ ] **Отформатируйте диск.** Мы будем использовать файловую систему `ext4`, стандартную для Linux.
    **ВНИМАНИЕ: Следующая команда сотрет ВСЕ данные на диске `/dev/sdX`. Убедитесь, что выбрали правильный диск.**
    ```bash
    # Замените /dev/sdX на ваш диск
    sudo mkfs.ext4 /dev/sdX
    ```

- [ ] **Создайте точку монтирования.** Это папка, к которой будет "привязана" наш диск.
    ```bash
    sudo mkdir /mnt/backup
    ```

- [ ] **Создайте резервную копию файла `/etc/fstab`:**
    ```bash
    sudo cp /etc/fstab /etc/fstab.bak
    ```

- [ ] **Настройте автоматическое монтирование.** Чтобы диск подключался сам после перезагрузки, нам нужно добавить его в `/etc/fstab`.
    - Сначала узнаем `UUID` нашего диска — это его уникальный идентификатор.
      ```bash
      # Замените /dev/sdX на ваш диск
      sudo blkid /dev/sdX
      ```
    - Скопируйте значение `UUID`.
    - Откройте `/etc/fstab` для редактирования:
      ```bash
      sudo vim /etc/fstab
      ```
    - Добавьте в конец файла новую строку:
      ```
      # Замените UUID на ваш
      UUID=ВАШ_UUID_ЗДЕСЬ    /mnt/backup    ext4    defaults    0    2
      ```
    - Проверьте, что все работает, выполнив команду монтирования:
      ```bash
      sudo mount -a
      ```
      Если ошибок нет, диск примонтирован в `/mnt/backup`.

### 2. Скрипт для резервного копирования

Мы будем использовать `rsync` — мощную утилиту для синхронизации файлов. Она копирует только те файлы, которые изменились, что делает процесс быстрым и эффективным.

- [ ] **Создайте директорию для скриптов.**
    ```bash
    mkdir ~/scripts
    cd ~/scripts
    ```

- [ ] **Создайте файл скрипта.**
    ```bash
    vim backup.sh
    ```

- [ ] **Добавьте в него следующее содержимое:**
    ```bash
    #!/bin/bash

    # Источник (что бэкапим)
    SOURCE="/srv/"

    # Назначение (куда бэкапим)
    DESTINATION="/mnt/backup/"

    # Запускаем rsync
    rsync -aAXv --delete "$SOURCE" "$DESTINATION"

    echo "Резервное копирование завершено: $(date)"
    ```
    *Ключ `--delete` означает, что если файлы были удалены в источнике (`/srv`), они будут удалены и в бэкапе. Это обеспечивает зеркальную копию.* 

- [ ] **Сделайте скрипт исполняемым.**
    ```bash
    chmod +x backup.sh
    ```

- [ ] **Проведите первый запуск вручную,** чтобы убедиться, что все работает.
    ```bash
    ./backup.sh
    ```

---

### 2.1. Улучшенная стратегия резервного копирования (Инкрементальные бэкапы с версионированием)

**⚠️ Важное замечание о стратегии резервного копирования:**
Текущая стратегия `rsync -aAXv --delete` создает точную зеркальную копию ваших данных. Это просто и эффективно для поддержания актуальной копии, но имеет **критический недостаток**: если исходные данные (`/srv`) будут повреждены или случайно удалены, эти изменения будут немедленно синхронизированы с резервной копией, что может привести к потере данных. Для более надежной защиты и возможности восстановления предыдущих версий файлов рекомендуется использовать **инкрементальные бэкапы с версионированием**.

Этот подход позволяет хранить несколько "полных" бэкапов, при этом на диске хранятся только уникальные версии файлов, что экономит место благодаря использованию жестких ссылок (hard links) для неизменившихся файлов.

- [ ] **Реализация инкрементальных бэкапов с жесткими ссылками (пример скрипта):**
    ```bash
    #!/bin/bash

    # Директория, которую бэкапим
    SOURCE="/srv/"
    # Корневая директория для бэкапов на внешнем диске
    BACKUP_ROOT="/mnt/backup/"

    # Формат даты для имени директории бэкапа
    DATE_FORMAT="+%Y-%m-%d_%H-%M-%S"
    CURRENT_DATE=$(date "$DATE_FORMAT")

    # Директория для текущего бэкапа
    CURRENT_BACKUP_DIR="${BACKUP_ROOT}daily.0/"
    # Директория для предыдущего бэкапа (для жестких ссылок)
    PREVIOUS_BACKUP_DIR="${BACKUP_ROOT}daily.1/"

    # --- Ротация бэкапов (пример: храним 7 ежедневных бэкапов) ---
    # Удаляем самый старый бэкап (daily.7)
    if [ -d "${BACKUP_ROOT}daily.7/" ]; then
        sudo rm -rf "${BACKUP_ROOT}daily.7/"
    fi

    # Сдвигаем все бэкапы на одну позицию (daily.6 -> daily.7, daily.5 -> daily.6 и т.д.)
    for i in $(seq 6 -1 0); do
        if [ -d "${BACKUP_ROOT}daily.${i}/" ]; then
            sudo mv "${BACKUP_ROOT}daily.${i}/" "${BACKUP_ROOT}daily.$((i+1))/"
        fi
    done

    # --- Создаем новый бэкап ---
    # Создаем директорию для нового бэкапа
    sudo mkdir -p "${CURRENT_BACKUP_DIR}"

    # Запускаем rsync с жесткими ссылками на предыдущий бэкап
    # --link-dest указывает rsync использовать файлы из PREVIOUS_BACKUP_DIR
    # если они не изменились, создавая жесткие ссылки вместо копирования.
    sudo rsync -aAXv --delete --link-dest="${PREVIOUS_BACKUP_DIR}" "$SOURCE" "${CURRENT_BACKUP_DIR}"

    echo "Инкрементальное резервное копирование завершено: $(date)"
    ```
    *Этот скрипт — пример. Его нужно будет адаптировать под ваши нужды, особенно в части ротации (например, добавить еженедельные/ежемесячные бэкапы).* 

- [ ] **Сделайте скрипт исполняемым.**
    ```bash
    chmod +x backup.sh # Убедитесь, что скрипт backup.sh исполняемый
    ```

- [ ] **Проведите первый запуск вручную,** чтобы убедиться, что все работает.
    ```bash
    ./backup.sh
    ```

- [ ] **Настройка Cron для инкрементальных бэкапов:**
    Откройте редактор заданий cron:
    ```bash
    crontab -e
    ```
    Замените текущую запись, если она есть, на вызов нового скрипта, например, каждую ночь в 3:00:
    ```
    # m h  dom mon dow   command
    0 3 * * * /home/tuchnyak/scripts/backup.sh > /home/tuchnyak/scripts/backup.log 2>&1
    ```
    *Не забудьте заменить `tuchnyak` на вашего пользователя в пути к скрипту.*
    *Конструкция `> ... 2>&1` перенаправляет весь вывод (и ошибки) в лог-файл, чтобы можно было проверить, как прошел бэкап.*

Теперь у вас есть полностью автоматизированная система резервного копирования.

## Глава 7: Развертывание собственных приложений с помощью Kamal

Эта глава посвящена самому интересному — развертыванию ваших собственных Java/Kotlin проектов на подготовленный сервер. Мы не будем копировать файлы вручную. Вместо этого мы будем использовать Kamal — современный инструмент, который автоматизирует весь процесс на профессиональном уровне.

### 1. Философия Kamal: Собрал локально -> Отправил в Registry -> Развернул на сервере

Kamal работает по принципу, который является стандартом в индустрии:

- [ ] **Сборка (Build):** Ваше приложение вместе со всей средой (нужная версия JDK, Kotlin, зависимости) упаковывается в единый, неизменяемый "коробок" — **контейнер-образ**. Этот процесс происходит **на вашей локальной машине для разработки**. Сервер в этом не участвует.
- [ ] **Публикация (Push):** Готовый образ загружается в **Container Registry**. Это "склад" для ваших образов, аналог GitHub для кода. Популярные варианты: Docker Hub, GitHub Container Registry.
- [ ] **Развертывание (Deploy):** Вы даете команду Kamal, и он подключается к вашему серверу по SSH и говорит ему: "Скачай с такого-то склада образ с такой-то версией и запусти его".

**Преимущества:**
- **Чистота:** Сервер никогда не видит вашего исходного кода и не "засоряется" инструментами сборки (JDK, Gradle, Maven).
- **Надежность:** Контейнер работает абсолютно одинаково на вашей машине и на сервере. Проблема "у меня работало, а на сервере — нет" исчезает.
- **Версионирование:** Вы можете легко откатиться на любую предыдущую версию вашего приложения, просто сказав серверу скачать старый образ.

### 2. Подготовка приложения: Dockerfile для Java/Kotlin

Чтобы Kamal мог собрать ваше приложение, ему нужна инструкция — `Dockerfile`. Этот файл должен лежать в корне вашего проекта.

- [ ] **Создайте `Dockerfile` в корне вашего проекта.**

Вот пример **многоэтапного (multi-stage)** `Dockerfile` для типичного Spring Boot / Ktor приложения, собранного с Gradle.

```dockerfile
# --- ЭТАП 1: СБОРКА ---
# Используем официальный образ с нужной версией JDK и Gradle
FROM gradle:8.5-jdk17-alpine AS builder

# Устанавливаем рабочую директорию внутри контейнера
WORKDIR /app

# Копируем файлы сборки, чтобы кэшировать зависимости
COPY build.gradle.kts settings.gradle.kts ./
COPY gradle ./gradle
COPY gradlew .

# Загружаем зависимости. Этот слой будет кэшироваться, если файлы не менялись.
RUN ./gradlew build --no-daemon || return 0

# Копируем весь исходный код
COPY src ./src

# Собираем приложение в исполняемый JAR-файл
RUN ./gradlew build --no-daemon


# --- ЭТАП 2: ЗАПУСК ---
# Используем минималистичный образ только с Java Runtime Environment (JRE)
FROM eclipse-temurin:17-jre-alpine

WORKDIR /app

# Копируем ТОЛЬКО собранный JAR-файл из предыдущего этапа
COPY --from=builder /app/build/libs/*.jar app.jar

# Указываем порт, на котором будет работать приложение
EXPOSE 8080

# Команда для запуска приложения при старте контейнера
ENTRYPOINT ["java", "-jar", "app.jar"]
```

### 3. Настройка Kamal в вашем проекте

- [ ] **Установите Kamal на ваш компьютер (не на сервер!).** Это делается через RubyGems.
    ```bash
    gem install kamal
    ```

- [ ] **Инициализируйте Kamal в проекте.** Находясь в корневой директории вашего приложения, выполните:
    ```bash
    kamal init
    ```
    Эта команда создаст директорию `.kamal` и основной конфигурационный файл `config/deploy.yml`.

- [ ] **Создайте файл `.env` в корне вашего проекта (рядом с `config/deploy.yml`).** В нем будут храниться секреты для Kamal и вашего приложения.
    ```bash
    vim .env
    ```
    Добавьте, например, пароль для Container Registry и любые другие секреты, которые нужны вашему приложению:
    ```
    KAMAL_REGISTRY_PASSWORD=your_registry_password
    DB_PASSWORD=your_app_db_password
    ```
    **ВАЖНО:** Добавьте `.env` в `.gitignore` вашего проекта, чтобы он не попал в Git.

- [ ] **Защитите файл `.env` правами доступа.**
    ```bash
    chmod 600 .env
    ```

- [ ] **Настройте `config/deploy.yml`.** Откройте файл:
    ```bash
    vim config/deploy.yml
    ```
    Приведите его к следующему виду, используя переменные из `.env`:
    ```yaml
    # Имя вашего сервиса (используется для имен контейнеров)
    service: my-java-app

    # Имя образа в Container Registry
    # Формат: <ваш_логин_в_registry>/<имя_образа>
    image: tuchnyak/my-java-app

    # Данные для входа в Registry. Kamal будет использовать их для `podman login`
    registry:
      server: docker.io # или ghcr.io
      username: tuchnyak
      # Ссылка на переменную окружения из .env файла
      password:
        - KAMAL_REGISTRY_PASSWORD

    # Настройки вашего сервера
    servers:
      web:
        hosts:
          - 192.168.1.100 # IP вашего домашнего сервера
        user: tuchnyak # Пользователь для SSH-подключения

    # Настройки контейнера
    # Kamal использует Traefik как обратный прокси по умолчанию. 
    # Мы будем использовать Nginx Proxy Manager, поэтому Traefik нам не нужен.
    # Закомментируйте или удалите секцию traefik, если она есть.
    # traefik:
    #   options:
    #     publish:
    #       - "8080" 
    
    # Переменные окружения для вашего приложения
    env:
      clear:
        # Пример: переменная, которая не является секретом
        APP_ENV: "production"
      secret:
        # Ссылка на секретную переменную из .env файла
        - DB_PASSWORD
    ```

### 4. Цикл развертывания

- [ ] **Первичная настройка сервера (`kamal setup`).** Эту команду нужно выполнить только один раз. Kamal зайдет на сервер и установит все необходимое (в нашем случае убедится, что Podman работает).
    ```bash
    kamal setup
    ```

- [ ] **Развертывание (`kamal deploy`).** Это ваша основная команда.
    ```bash
    kamal deploy
    ```
    Kamal выполнит все шаги за вас:
    - Соберет образ с помощью `Dockerfile` на вашем ПК.
    - Загрузит его в Registry.
    - Подключится к серверу.
    - Скачает новый образ.
    - Запустит новый контейнер и остановит старый.

- [ ] **Настройка в Nginx Proxy Manager (HTTPS).**
    - После первого деплоя вам нужно узнать, на какой порт хоста Kamal "приземлил" ваше приложение. Выполните на сервере `podman ps`. Вы увидите что-то вроде `0.0.0.0:32768->8080/tcp` (где `32768` — это случайный порт на хосте).
    - Перейдите в веб-интерфейс NPM (`http://192.168.1.100:81`).
    - `Hosts` -> `Proxy Hosts` -> `Add Proxy Host`.
    - **Domain Names:** `my-app.internal`.
    - **Scheme:** `http` (NPM будет общаться с контейнером по HTTP).
    - **Forward Hostname / IP:** `192.168.1.100`.
    - **Forward Port:** `32768` (порт, который вы увидели в `podman ps`).
    - **SSL:** Перейдите на вкладку `SSL`.
        - Включите `Force SSL`.
        - Выберите сертификат, который вы настроили в Главе 4 (Let's Encrypt DNS Challenge).
        - Нажмите `Save`.

Теперь у вас есть полный цикл CI/CD для ваших личных проектов, работающий по тем же принципам, что и в больших IT-компаниях.

## Приложение C: Двухфакторная аутентификация для SSH — два варианта

Двухфакторная аутентификация (2FA) — это критически важный слой безопасности. Даже если злоумышленник украдет ваш SSH-ключ, он не сможет войти на сервер без второго фактора. Ниже представлены два способа настройки 2FA.

### Вариант 1: Через USB-флешку (DIY-метод)

Этот метод добавляет физический фактор ("то, что у вас есть"), требуя наличия определенной флешки для входа. Это интересный пример для изучения работы системы, но он имеет серьезные риски и не рекомендуется для критически важных систем.

#### 1. Подготовка USB-флешки

- [ ] **Отформатируйте флешку** в файловую систему `ext4`.
- [ ] **Создайте на флешке файл-ключ.**
    ```bash
    # Подключите флешку и примонтируйте ее
    sudo mkdir /mnt/usbkey
    sudo mount /dev/sdX1 /mnt/usbkey # Замените /dev/sdX1 на ваш раздел флешки

    # Создайте файл-ключ
    sudo head -c 16 /dev/urandom | sudo tee /mnt/usbkey/ssh_key_file
    sudo chmod 400 /mnt/usbkey/ssh_key_file
    ```
- [ ] **Запишите UUID флешки.**
    ```bash
    sudo blkid /dev/sdX1
    ```
    Скопируйте `UUID`.

#### 2. Настройка сервера

- [ ] **Настройте автоматическое монтирование флешки.** Добавьте в `/etc/fstab` строку:
    ```
    UUID=ВАШ_UUID_ФЛЕШКИ_ЗДЕСЬ    /mnt/usbkey    ext4    defaults,nofail    0    2
    ```
    *Опция `nofail` важна, чтобы сервер загрузился, даже если флешка не подключена.*

- [ ] **Настройте PAM для SSH.** Откройте `/etc/pam.d/sshd` (`sudo vim /etc/pam.d/sshd`) и добавьте в самое начало файла строку:
    ```
    auth required pam_exec.so /usr/local/bin/check_usb_key.sh
    ```

- [ ] **Создайте скрипт `check_usb_key.sh`.**
    ```bash
    sudo vim /usr/local/bin/check_usb_key.sh
    ```
    Добавьте в него:
    ```bash
    #!/bin/bash
    KEY_FILE="/mnt/usbkey/ssh_key_file"
    if [ -f "$KEY_FILE" ]; then exit 0; else exit 1; fi
    ```
- [ ] **Сделайте скрипт исполняемым:**
    ```bash
    sudo chmod +x /usr/local/bin/check_usb_key.sh
    ```

- [ ] **Перезапустите SSH-сервис:**
    ```bash
    sudo systemctl restart sshd
    ```

#### 3. Анализ метода

**Преимущества:**
- **Защита от кражи ключей:** Защищает от удаленной атаки, если ваш SSH-ключ был скомпрометирован.
- **Нулевая стоимость:** Можно использовать любую старую флешку.

**Критические недостатки:**
- **Копируемость:** Файл-ключ на флешке можно легко скопировать. Если к флешке получат физический доступ, ее можно скомпрометировать.
- **Риск блокировки:** Если флешка потеряется или сломается, вы потеряете удаленный доступ к серверу. **Всегда имейте физический доступ к серверу для восстановления!**

**Вывод:** Интересный образовательный пример, но для реального использования настоятельно рекомендуется **Вариант 2**.

### Вариант 2: Через TOTP-приложение на телефоне (Рекомендуемый стандарт)

Этот метод использует стандартную технологию TOTP (Time-based One-Time Password) и приложение на вашем телефоне (Google Authenticator, Authy, 2FAS и т.д.) для генерации одноразовых кодов. Это надежно, удобно и является индустриальным стандартом.

#### 1. Установка

- [ ] **Установите PAM-модуль Google Authenticator на сервер:**
    ```bash
    sudo apt update
    sudo apt install -y libpam-google-authenticator
    ```

#### 2. Настройка для вашего пользователя

- [ ] **Запустите интерактивную настройку.** Выполните команду от имени вашего пользователя (**без `sudo`**):
    ```bash
    google-authenticator
    ```
- [ ] **Ответьте на вопросы:**
    - `Make tokens time-based (y/n)`: **y** (Да, делать токены основанными на времени).
- [ ] **Сохраните ваши данные:**
    Терминал покажет **большой QR-код**, **секретный ключ** и, что **самое важное**, **5 аварийных кодов восстановления (emergency scratch codes)**.
    1.  Отсканируйте QR-код вашим аутентификационным приложением на телефоне.
    2.  **ОБЯЗАТЕЛЬНО сохраните секретный ключ и аварийные коды в надежном месте** (например, в менеджере паролей). Если вы потеряете телефон, эти коды будут вашим единственным способом войти в систему.
- [ ] **Завершите настройку:**
    - `Update your "/home/user/.google_authenticator" file? (y/n)`: **y** (Да, обновить файл).
    - `Disallow multiple uses of the same authentication token? (y/n)`: **y** (Да, запретить повторное использование токена).
    - `Increase the time-skew window? (y/n)`: **n** (Нет, не увеличивать временное окно).
    - `Enable rate-limiting? (y/n)`: **y** (Да, включить ограничение на количество попыток).

#### 3. Настройка SSH-сервера

- [ ] **Настройте PAM.** Сообщите SSH, что нужно использовать новый модуль.
    ```bash
    sudo vim /etc/pam.d/sshd
    ```
    Добавьте в конец файла строку:
    ```
    auth required pam_google_authenticator.so
    ```

- [ ] **Настройте сам SSH-сервис.**
    ```bash
    sudo vim /etc/ssh/sshd_config
    ```
    Найдите и измените/добавьте следующие строки:
    ```
    # (Было) ChallengeResponseAuthentication no
    # (Стало) Позволяет SSH запрашивать у пользователя код
    ChallengeResponseAuthentication yes

    # Добавьте эту строку, чтобы требовать и ключ, и код
    AuthenticationMethods publickey,keyboard-interactive
    ```
    *`keyboard-interactive` — это механизм, через который PAM запрашивает TOTP-код.*

#### 4. Применение изменений

- [ ] **Перезапустите SSH-сервис.**
    ```bash
    sudo systemctl restart sshd
    ```

- [ ] **ПРОВЕРКА:**
    1.  **Не закрывая текущую сессию**, откройте **новое окно терминала**.
    2.  Попробуйте подключиться к серверу: `ssh tuchnyak@192.168.1.100`.
    3.  После того как ваш SSH-ключ будет принят, сервер попросит ввести код: `Verification code:`.
    4.  Введите 6-значный код из приложения на телефоне и нажмите Enter.
    5.  Если вход прошел успешно, настройка завершена. Если нет — вы можете исправить ошибки в старом окне терминала.

Теперь ваш SSH-доступ надежно защищен двумя факторами.

## Приложение D: Базовая конфигурация Vim

Чтобы работа с текстовыми файлами на сервере не вызывала дискомфорта, настроим Vim.

- [ ] **Создайте и откройте конфигурационный файл Vim:**
    ```bash
    vim ~/.vimrc
    ```

- [ ] **Добавьте в него следующие строки:**
    ```vim
    " Включаем подсветку синтаксиса
syntax on

" Устанавливаем цветовую схему, чтобы визуально отличать серверный Vim
colorscheme desert

" Включаем нумерацию строк
set number
" Включаем относительную нумерацию строк (показывает номер текущей строки и относительные номера для остальных)
set relativenumber

" Настройки отступов (4 пробела вместо табов)
set tabstop=4
set shiftwidth=4
set expandtab

" Постоянно показывать статус-бар
set laststatus=2
    ```

- [ ] **Сохраните и закройте файл** (нажмите `Esc`, затем введите `:wq` и `Enter`). При следующем открытии Vim применит все эти настройки.
